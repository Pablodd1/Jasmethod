JMM / INTERVALS ECOSYSTEM: 20-APP COMPARISON AND RELEASE GATES
Review date: 5 October 2026
Scope: products named in the owner's supplied Intervals.icu app directory;
current JMM integration findings supplied by the deployment reviewer;
official vendor documentation, product listings and first-party repositories.

DECISION

Keep JMM as the authoritative athlete profile, coaching plan, approval and
audit system. Keep DeepSeek. Intervals is the transport and interoperability
hub; optional companion apps fill particular ingestion or execution gaps.
Do not connect several autonomous planners as simultaneous writers of the
same calendar. Do not substitute an MCP connector for provider authorization
or device delivery. None of the 20 app listings proves JMM works end to end.

This comparison verifies documented product capabilities, not clinical
efficacy, prediction accuracy, an executed integration, or access to a
vendor's internal API. Prices are observed public consumer listings; they
are not negotiated commercial prices for 50 athletes. A directory listing
does not grant code reuse, data-processing rights or a commercial API license.

JMM's implemented path is:
  Garmin -> athlete's Intervals account -> JMM summary/wellness importer
  JMM approved run/bike prescription -> FIT -> athlete's Intervals calendar
  -> athlete's configured Garmin forwarding -> Garmin Connect -> watch.

Initial JMM import covers up to 180 days of AVAILABLE activity summaries
and wellness. It does not import an entire Garmin account/profile, all
historical records, sport-zone settings, GPS/HR/power streams or all FIT
details. Intervals must first possess and expose the relevant source data.
Incremental reads use a recent window. An old corrected record may need an
explicit backfill. Aggregated wellness can have incomplete source provenance.

Native publication currently supports run and bike FIT workouts. Automatic
new publication requires enabled server flags, the athlete's opt-in, current
day readiness and approval of the exact canonical revision. This is not
unconditional publication of every future session or every sport.
Provider acceptance is distinct from Garmin forwarding and watch receipt.
There is no verified watch receipt; JMM must not display "on your watch"
merely because Intervals accepted an event.

FIFTY ATHLETES: CAPACITY IS PLAUSIBLE, RELIABILITY IS NOT YET PROVEN

Current app dashboard limits: 8,000 requests/day, 2,500/15 minutes and an
additional 10 requests/second per IP. These observed app limits govern the
review; a public guide's 5,000 minimum differs and must not override the
actual client dashboard. Recheck before rollout or when limits change.

Illustrative lower-bound budget, not a load-test result:
* 50 athletes x 24 hourly polls x 2 endpoints = 2,400 daily read requests.
* Initial 180-day import in six 30-day chunks x 2 endpoints x 50 = 600 reads.
* Both exclude pagination where necessary, publication, reconciliation,
  webhook-triggered reads, retries, errors and manual sync requests.
* Concurrent imports can hit 10 requests/second despite a low daily total.
* Current sequential cron processing is not a sound 50-athlete capacity
  guarantee. Function timeouts, a slow athlete and repeated backfills must
  not block every later athlete.

Use durable per-athlete jobs, checkpointed backfills, bounded concurrency,
an app-wide rate governor, jitter, Retry-After-aware retry/backoff, leases
and deduplication. Prove this with load tests before broad activation.

PRIORITIZED IMPLEMENTATION TICKETS FOR THE NEXT PLATFORM

P0-A / Activation and one-athlete consent proof
Owner replaces exposed OAuth and webhook credentials in their secure
provider/hosting dashboards. Verify presence/configuration without logging
values. Confirm callback and webhook exact matches, necessary permissions,
server flags and cron availability. Complete a real athlete OAuth round trip.
Acceptance: correct athlete binding, encrypted stored token, no secrets in
logs, minimal scopes, denial/missing-scope/revocation behavior verified.
Do not report connection success on an authorization redirect alone.

P0-B / Tenant-safe durable ingestion and rate management
One job per athlete/provider/window; unique idempotency key; resumable
backfill cursor and actual coverage timestamps. Scheduler enqueues bounded
work instead of completing all athletes in a sequential request. A shared
governor accounts for daily, rolling-window and per-IP bursts, with headroom
for user requests. Use backoff/jitter, honor Retry-After, quarantine repeated
authorization errors and expose actionable failures.
Acceptance: a slow/failed athlete does not block others; restart resumes
without duplicate activities; duplicate webhook and concurrent cron collapse;
revoked tokens cannot resurrect; 50-athlete simulated load respects all
limits and runtime budgets. No live health data needed for synthetic load.

P0-C / Delivery, revision ownership and reconciliation
JMM is authoritative for its own published events. Stable external IDs,
exact canonical revision and remote-account binding must survive retries.
Publication/update/delete operations need an auditable receipt. Do not
delete or overwrite another planner's events. Reconcile approved edits,
cancellations, completed sessions and disconnects explicitly.
Acceptance: one published event per approved session; duplicate retries do
not duplicate workouts; edited targets replace the correct event; canceled
workouts disappear; remote failures remain failed/unknown, not delivered.
Display separate stages: JMM prepared, Intervals accepted, Garmin Connect
observed, watch confirmed. Record manual hardware verification when no
provider device receipt exists. Test minutes/seconds, miles/km, pace/speed,
power/HR, repeats, rests, dates/timezones/DST, warm-up and cool-down.

P1-A / Profile, threshold and provenance import
Inventory Intervals settings/profile API fields before adding scope. If
SETTINGS:READ is required, request incremental explicit consent; never
silently expand authorization. Do not call Intervals settings a full Garmin
profile. Store values as observations: metric, units, source/provider/device,
remote ID, measured-at, imported-at, method, quality and effective period.
Store manual/coach overrides separately; imported values must not erase
them. Present disagreements and stale zones for review, not silent overwrite.
Acceptance: profile/zone history is explainable; unknown source remains
unknown; SDNN and RMSSD are distinct; tests cover units, timezone, duplicates,
missing fields, invalid values, stale thresholds and conflicting devices.

P1-B / Activity detail required for analysis
Add explicitly authorized, paginated and checkpointed raw-detail/stream/FIT
fetches only for the analyses JMM supports. Keep raw imported evidence
separate from derived metrics. Define storage, deletion and retention.
Acceptance: interval compliance, terrain analysis or durability charts cite
actual available samples; missing streams show an explanation rather than
invented precision. Every derived metric carries algorithm/version metadata.

P1-C / Source restrictions and wellness attribution
Maintain source allowlists and source-level usage rights throughout imports,
merges, exports, dashboards and DeepSeek context construction. Do not treat
an Intervals or another bridge copy of restricted data as unrestricted.
Unknown-source data must not silently become AI training/coach data. Separate
AI inference from model training; both must satisfy applicable provider
terms and athlete consent. Use minimal task-relevant context, not whole
health histories by default. Honor disconnection/deletion requirements.
Acceptance: restricted sources cannot enter blocked AI/coaching/export
paths; mixed-source fields retain attribution; logs omit health payloads,
tokens and private identifiers; tests prove owner/coach scope isolation.

P1-D / Device-free daily coaching and recovery
Offer short manual/voice inputs: available time, sleep duration and quality,
fatigue, stress, mood, motivation, soreness location/severity, illness signs,
session RPE, actual food/fluid intake and GI tolerance. Keep unknown distinct
from zero. Let athlete and coach correct the extracted facts, then record
who changed them. Missing devices must not fabricate objective biometrics.
Acceptance: no-device athletes get an explained conservative prescription;
illness/pain escalation overrides scheduled intensity; rest remains rest
when required; competing edits produce one reviewed revision.

P2-A / Optional companion qualification
Pilot Watchletic and HealthFit first, then Health Sync for missing ingestion
sources, TrainerDay/Cadence for execution, ErgZone after sport support.
Maintain a compatibility matrix with sport, direction, fields, required
subscription, device model/firmware, tested date and known limitations.
Do not label an untested app as supported because it appears in the directory.

P2-B / Fueling and race strategy
Deterministic calculators own numerical prescriptions; DeepSeek explains
their inputs and evidence. Version formulas and distinguish recommendation,
user-reported intake and measured values. Nutrition depends on planned and
actual workload, tolerance, preferences and clinically relevant constraints;
do not infer exact glycogen use from a load score. Support coach overrides.
Race predictions need course/terrain/weather inputs, data-quality warnings,
uncertainty intervals and prospective/out-of-sample validation. Product
marketing and a cited paper are not validation of JMM's implemented model.

ROLLOUT ACCEPTANCE: ONE -> FIVE -> FIFTY

1 ATHLETE: credential rotation confirmed; consent returns to correct JMM
account; known Garmin activity and wellness values compare correctly;
available-history coverage visible; approved run and bike accepted by
Intervals, observed in Garmin Connect and opened with correct steps on a
real compatible watch. Complete a short test activity and prove return and
plan matching. Test edit/cancel, duplicate webhook, disconnect and reconnect.
Store dates, revisions, redacted evidence and exact hardware—not assertions
based solely on a green unit suite or provider HTTP 200.

5 ATHLETES: separate permissions and histories, at least two device models,
different timezones, one no-device athlete, one intermittent/offline device,
one consent/reconnect failure. Verify no cross-account visibility or
publication. Observe a complete operational cycle including automatic
ingestion, daily adaptation, approval, delivery and completion import.

50 ATHLETES: synthetic capacity tests first, then staged real onboarding
with each athlete's consent. Demonstrate bounded queue age, no missed jobs,
request-limit headroom, isolated failures, duplicate prevention, retry
recovery, daily monitoring and a rollback/disable path. Define numerical
latency/error objectives before the test, measure against them and publish
failures. Do not infer real-world readiness from the arithmetic budget.

FINAL POSITION

The architecture supports the intended two-direction Garmin workflow via
Intervals, subject to per-athlete permissions, available data, supported
workout formats and compatible devices. Current evidence does not establish
that JMM has completed that workflow for one athlete, much less 50. The
immediate blocker is unverified replacement/configuration of credentials;
the next gates are real OAuth, hardware round-trip acceptance and reliable
per-athlete scheduling. Broadening the app ecosystem comes after these
foundations. DeepSeek remains in place.
